## I. AI Instructions

### Context

During your learning journey, AI can assist with many different tasks. Take the time to explore AI tools and understand how they can support your work. However, always be cautious and critically assess the results. Whether it is code, documentation, ideas, or technical explanations, you can never be completely sure the prompt was well-formed or the output is accurate. Your peers remain an essential resource to catch mistakes and blind spots.

### Main Message

- Use AI to reduce repetitive or tedious tasks.
- Develop prompting skills, both coding and non-coding, that will benefit your future career.
- Learn how AI systems work so you can anticipate and avoid risks, biases, and ethical issues.
- Keep building both technical and soft skills by working with your peers.
- Only use AI-generated content that you fully understand and can take responsibility for.

### Learner Rules

- Take time to explore AI tools and understand how they work so you can use them ethically and reduce bias.
- Reflect on the problem before prompting. Better thinking leads to clearer and more relevant prompts.
- Systematically check, review, question, and test anything generated by AI.
- Always seek peer review instead of relying only on your own validation.

### Phase Outcomes

- Develop both general-purpose and domain-specific prompting skills.
- Improve productivity through effective AI usage.
- Continue strengthening computational thinking, problem-solving, adaptability, and collaboration.

### Comments and Examples

- In exams and evaluations, you will need to demonstrate real understanding.
- Explaining your reasoning to peers often reveals gaps in your understanding.
- AI lacks your full project context and often gives generic answers.
- Peers can offer alternative perspectives and act as a quality checkpoint.

**Good practice:** Ask AI for ideas, test them yourself, and review the result with a peer.  
**Bad practice:** Copy AI-generated code you do not understand and fail to explain it during evaluation.

## II. Preamble

You are entering the final project of the Common Core. It is a group project for 4 to 5 people and is intended to develop creativity, self-confidence, adaptability to new technologies, and teamwork skills.

You will create a real-world web application as a team. The project is divided into:

- A mandatory part, which is the fixed core of the project and must involve every team member.
- A set of modules, which you choose and which count toward the final grade.

This is a long project. Poor early decisions and weak coordination will cost time. Project management and team organization strongly affect the result. All team members must actively contribute to both the mandatory part and the modules.

### II.1 Team Organization and Project Management

Proper team organization is crucial. You must establish clear roles and responsibilities from the start.

#### II.1.1 Required Team Roles

Your team must assign the following roles. With 4 members, one person may have multiple roles.

- **Product Owner (PO)**
  - Defines the product vision.
  - Prioritizes features.
  - Ensures the project meets user needs.
  - Maintains the product backlog.
  - Makes decisions on features and priorities.
  - Validates completed work.
  - Communicates with stakeholders such as evaluators and peers.

- **Project Manager (PM) / Scrum Master**
  - Facilitates team coordination.
  - Removes obstacles.
  - Organizes meetings and planning sessions.
  - Tracks progress and deadlines.
  - Ensures team communication.
  - Manages risks and blockers.

- **Technical Lead / Architect**
  - Oversees technical decisions and architecture.
  - Defines the technical architecture.
  - Chooses the technology stack.
  - Ensures code quality and best practices.
  - Reviews critical code changes.

- **Developers (all team members)**
  - Implement features and modules.
  - Write code for assigned features.
  - Participate in code reviews.
  - Test their implementations.
  - Document their work.

**Team size guidance**

- 4 people: some members will hold multiple roles, for example `PM + Developer` or `PO + Developer`.
- 5 people: roles can be more specialized, for example dedicated `PO`, `PM`, `Tech Lead`, and 2 `Developers`.

All roles must be clearly documented in `README.md`.

#### II.1.2 Recommended Project Management Practices

These practices are strongly recommended:

- Meet regularly, weekly or bi-weekly, to sync on progress and blockers.
- Use simple task management tools such as GitHub Issues, Trello, or a shared document.
- Break work into smaller manageable tasks.
- Have at least one other team member review important code changes when possible.
- Document key decisions and how the project works.
- Use a communication channel like Discord or Slack.

During evaluation, the team may be asked to explain:

- How roles were distributed.
- How work was organized and divided.
- How the team communicated and coordinated.
- How each member contributed.

All team members must be able to explain the project and their own contributions.

## III. Mandatory Part

The project content is up to the team. You must bring your own idea and decide together what web application to build. You are not fully free because there are constraints, but the application concept is yours.

### III.1 What Are We Doing?

You must create a comprehensive `README.md`. Detailed requirements are defined later in the document.

Valid project examples include:

- A multiplayer Pong game with a tournament system.
- A collaborative platform with real-time features.
- A social network with user interactions.
- An online game such as Chess or Tic-Tac-Toe with matchmaking.
- A project management application.
- Any other creative web application that meets the requirements.

The goal is to build something engaging that demonstrates technical skill and creativity.

### III.2 General Requirements

If these requirements are not respected, the project will be rejected.

- The project must be a web application with a frontend, backend, and database.
- Git must be used with clear and meaningful commit messages.
- The repository must show:
  - Commits from all team members.
  - Clear commit messages describing changes.
  - Proper work distribution across the team.
- Deployment must use a containerization solution such as Docker or Podman and run with a single command.
- The website must be compatible with the latest stable version of Google Chrome.
- No warnings or errors should appear in the browser console.
- The project must include accessible Privacy Policy and Terms of Service pages with relevant content.

**Privacy Policy and Terms of Service**

- They must be easily accessible from the application, for example from the footer.
- They must contain relevant and appropriate content.
- They must not be empty or placeholder pages.

Missing or inadequate Privacy Policy / Terms of Service pages will result in project rejection.

**Multi-user support is mandatory**

Your application must support multiple users simultaneously. This includes:

- Multiple users being logged in and active at the same time.
- Concurrent actions by different users being handled properly.
- Real-time updates being reflected across connected users where applicable.
- No data corruption or race conditions from simultaneous actions.

### III.3 Technical Requirements

These requirements are also mandatory.

- The frontend must be clear, responsive, and accessible across all devices.
- Use a CSS framework or styling solution of your choice, such as Tailwind CSS, Bootstrap, Material-UI, or Styled Components.
- Store credentials such as API keys and environment variables in a local `.env` file ignored by Git, and provide an `.env.example`.
- The database must have a clear schema and well-defined relations.
- The application must include a basic user management system with secure signup and login.
  - At minimum, email and password authentication with proper security, including hashed and salted passwords.
  - Additional methods such as OAuth or 2FA can be implemented through modules.
- All forms and user input must be validated in both frontend and backend.
- Any connection to the backend from a browser, script, or external API must use HTTPS.
  - Internal backend connections, such as between the web server and database inside containers, may be unencrypted.

**What counts as a framework in this project**

A framework is considered a comprehensive tool that provides:

- Structured architecture and conventions for organizing code.
- Built-in features for common tasks such as routing or state management.
- A complete ecosystem of tools and libraries.

Examples:

- Frontend frameworks: React, Vue, Angular, Svelte, Next.js
- Backend frameworks: Express, Fastify, NestJS, Django, Flask, Ruby on Rails
- Not frameworks: jQuery, Lodash, Axios

For this subject, React is considered a framework because of its ecosystem and architectural patterns.

  - Other significant technologies or libraries.
  - Justification for major technical choices.

The README is a critical evaluation artifact. It must be:

- Clear and well organized.
- Complete.
- Professional and easy to read.
- Honest about contributions and challenges.

A poor or incomplete README can negatively affect evaluation.

**The README must be written in English.**

## VII. Bonus Part

The bonus part is considered only if all required modules have been implemented and the minimum 14 mandatory points are validated.

Each extra validated module beyond the required 14 points may count as bonus:

- Major module: `2` points
- Minor module: `1` point

Each extra module must:

- Be fully functional.
- Meet the module requirement description.
- Add real value to the project.
- Include proper justification in the README.

The maximum possible bonus is **5 points**.

Examples:

- `5` minor modules
- `2` major modules + `1` minor module

## VIII. Submission and Peer-Evaluation

Submit the assignment in the Git repository as usual. Only the work inside the repository will be evaluated, so file names must be checked carefully.

It is strongly recommended to discuss ideas with the team and peers before starting implementation.

During evaluation, a brief project modification may sometimes be requested. It can include:

- A minor behavior change.
- Writing or rewriting a few lines of code.
- Adding a small feature.
- Modifying a display.
- Adjusting a data structure to store new information.

This step is intended to verify actual understanding of a specific part of the project.

- The modification can be performed in any development environment you choose.
- It should be feasible within a few minutes, unless the evaluation guidelines specify otherwise.
- The exact details depend on the evaluation guidelines and may vary between evaluations.
