# Bug Audit — 2026-07-04

Deep-dive review of the Transcendence backend, frontend and infra layers. Each
entry is written so another agent can fix it without re-discovering context:
severity, exact location, what's wrong, why it matters to users, and a
suggested direction. **No fixes have been applied.** Line numbers are as of this
commit and may drift.

Severity scale:
- **Critical** — security hole or data corruption reachable in production.
- **High** — wrong results users see/act on, or a broken core flow.
- **Medium** — real defect with a workaround or narrow trigger.
- **Low** — polish, fragility, or edge-case-only.

## Critical

### C1 — Rate limiter is trivially bypassable via `X-Forwarded-For` spoofing
**Location:** `backend/src/modules/auth/rate-limiter.service.ts` → `getIp()` (~L58-64); nginx `infra/reverse-proxy/conf/default.conf.template` (all `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`).

`getIp()` takes the **first** token of `X-Forwarded-For`:
```ts
const forwarded = req.headers["x-forwarded-for"];
if (typeof forwarded === "string") return forwarded.split(",")[0].trim();
```
nginx uses `$proxy_add_x_forwarded_for`, which **appends** the real client IP to
whatever the client sent. So the header becomes `"<client-supplied>, <realIP>"`
and the limiter keys off `<client-supplied>`. An attacker rotates the first
token per request and gets unlimited attempts.

**Impact:** Defeats every limiter built on this service — login (10/min),
register (5/min), guest creation (10/min), casino spins (30/min), gif search.
Enables credential brute-force and resource abuse.

**Fix direction:** Trust only the proxy-derived IP. Since `app.set("trust proxy", 1)` is set in `main.ts`, prefer Express's `req.ip`, or use the **last** XFF entry, or read `X-Real-IP` (nginx sets `$remote_addr`). Do not trust the client-controlled left-most token.

### C2 — CORS allowlist uses `startsWith`, allowing look-alike origins with credentials
**Location:** `backend/src/main.ts` L28-37.

```ts
if (allowed.some((o) => origin.startsWith(o.trim()))) return callback(null, true);
```
`startsWith` matches by prefix, so an allowlist entry `https://localhost` also
accepts `https://localhost.attacker.com`, and `https://app.example.com` accepts
`https://app.example.com.evil.io`. Combined with `credentials: true`, a
malicious origin can make authenticated cross-origin requests.

**Impact:** Cross-origin credential theft / CSRF-adjacent abuse from attacker-controlled domains.

**Fix direction:** Compare origins for **exact equality** against a normalised allowlist (parse both with `new URL()` and match on origin), not prefix.

## High

### H1 — Ranked ELO is computed from partially-updated ratings (order-dependent, not zero-sum)
**Location:** `backend/src/modules/matchmaking/game-session.service.ts` → `applyEloRatings()` (~L200-245).

The loop mutates `rating.rating` in place **and** reads opponents' ratings from
the same `ratings` array inside the loop:
```ts
for (let i = 0; i < room.players.length; i++) {
  ...
  const opponentRatings = ratings.filter((_, j) => j !== i).map((r) => r.rating);
  ...
  rating.rating = Math.max(0, playerRating + delta); // mutates array in place
  await ratingRepo.save(rating);
}
```
By iteration `i=1`, player 0's rating has already been overwritten, so player 1's
expected score is computed against a post-update value. Ratings become
order-dependent and no longer conserve points.

**Impact:** Incorrect ranked ELO for every finished ranked match, visible on
leaderboards. Worse with >2 players.

**Fix direction:** Snapshot all pre-match ratings into a separate `const` array first, compute every player's delta against that immutable snapshot, then apply/save.

### H2 — Monthly / weekly leaderboards silently show all-time numbers
**Location:** `backend/src/modules/users/users.controller.ts` → `queryPeriod()` (~L300-345).

The period cutoff is applied inside the **JOIN condition**, not a WHERE, and the
win count doesn't require the match to be in-window:
```sql
LEFT JOIN match_players mp ON mp."userId" = u.id
LEFT JOIN matches       m  ON m.id = mp."matchId" AND m."createdAt" >= $1
...
COALESCE(SUM(CASE WHEN mp.outcome = 'win' THEN 1 ELSE 0 END),0)::int AS wins,
COALESCE(COUNT(mp.id),0)::int AS "gamesPlayed"
```
Because `mp` is joined without the date filter, rows for out-of-window matches
still appear (with `m` = NULL) and `mp.outcome = 'win'` still counts. `wins`
and `gamesPlayed` therefore reflect **all time**, not the requested period.

**Impact:** `period=weekly` and `period=monthly` return the same data as
`period=all`. The feature is effectively broken for users.

**Fix direction:** Filter by window on the fact table, e.g. `SUM(CASE WHEN mp.outcome='win' AND m.id IS NOT NULL THEN 1 ELSE 0 END)` and `COUNT(m.id)`, or move `m."createdAt" >= $1` into `WHERE` with an inner join for the counted rows. Add a test asserting weekly ≠ all-time when old wins exist.

## Medium

### M1 — Public matchmaking ignores the `powerupsEnabled` toggle
**Location:** `backend/src/modules/matchmaking/matchmaking.service.ts` → `joinQueue()` L45-99.

`powerupsEnabled` is read from the payload and stored on the queue entry, but
`createRoom` is called with a hard-coded literal:
```ts
const powerupsEnabled = payload.powerupsEnabled ?? true; // computed…
...
const room = this.roomService.createRoom(match.id, gameId, mode, players,
  { powerupsEnabled: true });                            // …but ignored
```
A player who queues with powerups **off** still lands in a powerups-on match.

**Fix direction:** Pass the resolved value: `{ powerupsEnabled }`. Decide whose preference wins when two queuers disagree (host/first-in-queue), and document it.

### M2 — Demo account is force-seeded in every environment, including production, with weak default credentials
**Location:** `backend/src/modules/auth/auth.service.ts` → `seedDemoAccount()` (L277-314); `docker-compose.yml` L115 `DEMO_PASSWORD=${DEMO_PASSWORD:-KameMaster42}`.

`onApplicationBootstrap` always seeds a full username/password account
(`KameMaster` / `KameMaster42` by default) and tops its balance to 1e9 coins on
every boot. There is no environment gate, so production ships a known-credential
login unless `DEMO_USERNAME`/`DEMO_PASSWORD` are overridden.

**Impact:** Predictable backdoor account in prod. Contradicts the "no hardcoded
credentials / gate dev features behind env flags" standard.

**Fix direction:** Gate seeding behind `NODE_ENV !== 'production'` **and** an explicit `ENABLE_DEMO_ACCOUNT` flag; refuse to seed in prod when the password is still the default. Never commit a default password.

### M3 — Duplicate DM conversations can be created under a race
**Location:** `backend/src/modules/chat/chat.service.ts` → `getOrCreateDirectConversation()` (L148-208); `entities/conversation.entity.ts` (no unique pair constraint).

The "find existing DM, else create" logic isn't atomic and there's no DB
constraint enforcing one DM per user pair. Two near-simultaneous
`POST /chat/conversations/direct` (e.g. double-click, both users opening at
once) create two DM rows; messages then split across two threads.

**Fix direction:** Add a canonical unique key for DM pairs (e.g. a `dmKey` column = `min(a,b)+":"+max(a,b)` with a unique index) and upsert/catch `23505`, or serialise creation.

### M4 — Achievement coin rewards aren't reflected in the progression response
**Location:** `backend/src/modules/game-results/game-results.service.ts` → `submitResult()` (L46-110); `achievements/achievements.service.ts` → `applyReward()` (coins branch saves user again).

`submitResult` computes `newCoins` **before** calling
`achievementsService.evaluateForUser(user)`, which may grant coin rewards and
save the user a second time. The returned `ProgressionResult.newCoins` omits
those coins, so the client's balance/animation is wrong until the next refetch,
and the user row is saved twice in one flow.

**Fix direction:** Evaluate achievements first (or re-read the user's coins after evaluation) and return the final balance. Consider folding both writes into one transaction.

### M5 — Friend-request creation returns 500 instead of 409 on the unique-index race
**Location:** `backend/src/modules/friends/friends.service.ts` → `sendRequest()` (L62-118); `block()` (L~200-230).

`sendRequest` does check-then-insert; if two requests race (or a request crosses
with the reverse-direction one), the `@Index(unique)` on `friendships` throws a
`23505` that isn't mapped, so the caller gets a generic 500 instead of the
intended `ConflictException`. `block()` similarly does delete-then-insert
outside a transaction (except when called from `ReportsService`), leaving a
brief window where a concurrent op can interleave.

**Fix direction:** Catch driver `code === '23505'` in `sendRequest` and surface `ConflictException`. Wrap `block()`'s delete+insert in a transaction (or upsert).

### M6 — Legit winners can be denied match rewards if their socket blips at match end
**Location:** `backend/src/modules/matchmaking/game-session.service.ts` → `persistFinishedRoom()` (progression loop: `if (!player.connected) continue;`).

Progression (XP, coins, card drop, stats via `submitResult`) is only granted to
players whose `connected` flag is true at persistence time. A player who wins
but whose socket momentarily drops right as the final scoring input lands gets
`match_players.outcome = 'win'` recorded but **no** XP/coins/card. The
match-history and the reward path disagree.

**Fix direction:** Base reward eligibility on participation/outcome, not the live socket flag, or grant on reconnect. At minimum, document the intent if this is deliberate anti-farming.

## Low

### L1 — Non-GET requests aren't retried on transient 5xx, unlike GETs
**Location:** `frontend/src/features/hub/api.ts` → `apiFetch()` (L127-166).

Transient statuses (502/503/504) are retried only for `GET`. A `POST` (spin,
send message, submit result) issued during a brief backend restart fails
immediately with an `AuthError`, surfacing a hard error to the user even though
a single retry would likely succeed. Ensure retried non-GET requests remain idempotent or are safe to repeat before enabling this.

**Fix direction:** Allow one bounded retry for idempotent/safe non-GET calls, or at least surface a friendlier "try again" state.

### L2 — `apiUploadFile` unconditionally parses JSON
**Location:** `frontend/src/features/hub/api.ts` → `apiUploadFile()` (L171-210).

Returns `res.json()` with no 204/empty-body guard (unlike `apiFetch`, which
handles 204). Works today because avatar upload returns JSON, but any future
empty-body upload response throws a parse error.

**Fix direction:** Mirror the 204/empty-body handling from `apiFetch`.

### L3 — Profile hover-card cache is never invalidated within a session
**Location:** `frontend/src/features/social/profileCard/cache.ts`.

`createProfileCardCache` caches by username with no TTL/invalidation. If a
friend levels up, changes avatar or tag mid-session, their hover card shows
stale data until reload.

**Fix direction:** Add a short TTL, or invalidate on the relevant `user:updated`/presence events.

### L4 — `submitResult` assumes `user.profile` is always present
**Location:** `backend/src/modules/game-results/game-results.service.ts` → `submitResult()` (profile stats block).

`profile.totalWins += 1` etc. dereference `user.profile` without a null guard. A
user row missing its eager-loaded profile (data-integrity edge, partial
migration) throws mid-flow and the whole result submission 500s.

**Fix direction:** Guard for a missing profile (create-on-demand or fail with a clear error) before mutating stats.

### L5 — `grantMatchDrop` can race to a `23505` on concurrent first-copy inserts
**Location:** `backend/src/modules/cards/cards.service.ts` → `grantCard()` via `grantMatchDrop()` (non-transactional repo path).

`grantCard` does `findOne` then insert on the shared repo (no transaction for
match drops). Two concurrent match completions rolling the player's first copy
of the same card can both miss the row and one insert hits the unique
constraint; it bubbles as a 500 (swallowed as best-effort in `submitResult`, so
the drop is silently lost).

**Fix direction:** Upsert / catch `23505` and re-read to increment.

## Notes / verified-NOT-bugs (to save the next agent time)

- **Match finish path for throw-based games is fine.** The gateway's early-return
  throw branches (`game:input` handler) don't call `finishIfEnded`, but all four
  engines transition to `finished` on a *scoring/settled* action
  (`round:score` / `settled`), which falls through to the `finishIfEnded` +
  `game:end` tail. Verified in bamboo-bash, bell-clash, kame-knock, shell-curl.
- **Casino money movement is sound.** Spins run under a pessimistic write-lock in
  one transaction; nonce/seed fairness holds; balance checks are inside the lock.
- **`secrets/` is git-ignored** (`.gitignore` L20) and not tracked — the pem/vault
  files on disk are local only, not committed.
- **Password hashing** (scrypt + per-user salt + `timingSafeEqual`, constant-time
  dummy on missing user) is correct.
